Adjustability Documentation Help

Mechanics

Main Functionality

Adjustability's main functionality is to enable the Player to toggle between Mutually Exclusive Enchantments of an Item (ItemStack Class), of course if that particlar item meets that condition.

Example

If an item, for instance Diamond Pickaxe, is enchanted with 2 Mutually Exclusive Enchantments, let's say Fortune III and Silk Touch, the mod should have a mechanism which chooses one of those Enchantments (More details on how that's chosen later) to be active on the item (because Mutually Exclusive Enchantments shouldn't stack).

So, some sort of ItemStack.disable(Enchantment e) or Enchantment.disable(ItemsStack i) method would be really helpful.

The issue is the way Minecraft and the Forge API handle Enchantments.

    Default Enchantment Handling

    Now, there isn't anything inherently wrong with the way Enchantments are handled by default, all of the EnchantmentHandler methods do their job as intended, but for the purposes of Adjustability it leaves a lot to be desired.

    If you wanted to 'disable' an enchantment on an item, there's no direct way of doing that. The EnchantmentHandler class doesn't provide such methods. Instead, if you wanted 'disable' a certain enchantment you would need to completely remove that enchantment from the item, essentially 'disabling' it.

    Now, You might think:

    'Why don't you just create a custom enchantment class that inherits from the existing Enchantment class and implement that funcionality?'

    I don't like that solution because then the mod would have to copy over the objects from the Enchantment class and instatiate objects based off of my CustomEnchantment class. This just adds unecessary object's onto the memory and creates a middle-man between enchantable entities and base enchantments.

    The approach is to come up with the least invasive way to handle data.

    One way, which is actually pretty invasive, is to persist the Mutually Exclusive Enchantment data again to the ItemStack NBT data.

    ItemStack ComponentData

    {enchantments: [ {silk_touch}, {fortune}, {efficiency} ] } ...rest of the nbt data... + {enchantments: [ + {silk_touch}, + {fortune} + ] + }

    Then this ItemStack will persist the data that's necessary for Adjustability.

    The downside is of course that this approach is very invasive, because this data is persisted at the vanilla level. Meaning that if a player removes Adjustability .jar file, the additional enchantment data will be persisted forever.

    Solution

    The way most other mods handle data is by persisting data in their own custom directories, creating a custom database.

    This is the approach that was chosen because:

    • Non-invasive - No vanilla data is affected

    This is possible because each ItemStack object has a unique identifier (it's not universally unique like a UUID, it's unique in the context of the server/game instance), we can make entries to our custom 'table' which stores the different mutually exclusive enchantments based off of the ItemStack it's asosciated with.

    Adjustability essentially splits every ItemStack object into 2 distinct categories:

    • ItemStack objects with Mutually Exclusive Enchantments

    • ItemStack objects without Mutually Exclusive Enchantments

    Practical Example of an ItemStack reaching the Mutually Exclusive ItemStack Category

    1. There exists a Diamond Pickaxe with exactly 1 Enchantment:

      1. Fortune

    2. The ItemStack object for this Diamond Pickaxe will have a unique identifier, let's say 1.

    3. The player then places that Diamond Pickaxe with Fortune in the left slot of the Anvil and an Enchantment book with only Silk Touch on it in the Anvil's right slot.

    4. The vanilla enchantment mechanics block the action of combining Enchantments from these ItemStacks because Fortune and Silk Touch are Mutually Exclusive Enchantments.

    5. The action of placing an item in the Anvil is a Game Event. This Event can be targeted by a custom method with the @EventSubscriber annotation.

    6. Using the Event, a custom method can check if combining the two items would result in an ItemStack with Mutually Exclusive Enchantments. It checks against a Data Class which stores the Mutually Exclusive Enchantments and their relations (this is loaded into memory from persisted storage).

    7. In this example, this process would result in a Diamond Pickaxe with Fortune and Silk Touch, which are Mutually Exclusive Enchantments. Because this ItemStack would reach the Mutually Exclusive ItemStack Category, it's data related to the mod would be stored in a custom database.

    8. The ItemStack with the unique identifier 1 would be stored in a custom database, alongside entries for it's Mutually Exclusive Enchantments.

    9. Using the Event, the method can intercept the event and apply the Mutually Exclusive Enchantment anyway.

    10. Now there exists a Diamond Pickaxe with 2 Mutually Exclusive Enchantments:

      1. Silk Touch

      2. Fortune

    11. Suppose that these 2 enchantment have a unique identifier of 1 and 2 respectively. The ItemStack with the unique identifier 1 would be stored in a custom database, alongside entries for it's Mutually Exclusive Enchantments. This 'file' will be present at the World level:

      1: [1, 2]
